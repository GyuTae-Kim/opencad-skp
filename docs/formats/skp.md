# SketchUp(.skp) 형식 조사 기록

SketchUp 파일은 공개 명세가 없는 비공개 이진 형식이다. 이 문서의 출처는 둘이다: **공개 표본 바이트로 추론** + **2026-10 비공개 참조 해석기(SketchUp C API를 비교 기준으로 맞춘 해석기, 아래에서는 "엔진")의 형식 지식을 옮김**.
- 처음(2026-09)에는 인터넷에 공개된 표본 파일의 바이트만 직접 들여다보고 추론했다. SketchUp SDK·Ruby API·다른 SKP 읽기 프로그램·플러그인의 코드는 보지 않았고, 설치된 SketchUp도 실행하지 않았다.
- 2026-10에는 사용자의 허락을 받아 엔진(파이썬)에서 SKP를 읽는 부분의 문서·코드에서 형식 지식(꼬리표의 뜻·값 꼴·읽기 규칙)을 옮겼다.
  2020 이하(MFC 객체 직렬화) 해석도 같은 때 엔진의 legacy 해석기와 문서의 2020 이하 절에서 옮겼다(엔진은 MFC 직렬화의 공개 설명 Microsoft TN002·CArchive 문서를 출처로 적었다). 엔진은 SketchUp 2026 C API로 만든 표준 파일과 C API 기대값을 비교 기준으로 맞춘 해석기다. 코드는 옮기지 않고 opencad-skp 꼴로 새로 썼다. 엔진의 표준 파일은 읽기 전용으로 찍어 보기만 했고 저장소·시험에는 넣지 않았다(시험은 아래 구조를 손으로 옮긴 바이트로 한다).
- 아래 표의 ✔ 중 "엔진"이라고 적은 것은 엔진이 C API와 견주어 맞춘 것이고, ◐는 엔진도 추정(말뭉치 관찰)이라고 적은 것이다.
- 형식이 아닌 화면 규칙(모형 단위 글, 매끈한 모서리 건너 꼭짓점 법선 평균 문턱, 치수선·끝 표시 그리기, 장면 적용 차례, 줄자 추정 차례)은 같은 때 비공개 참조 뷰어(웹 SKP 뷰어)의 규칙을 참고해 앱(`src/app/`)과 장면 출력(`src/scene-*.ts`)에 새로 썼다.
- 무늬(텍스처, 2026-10-16)도 같은 길로 옮겼다: 면 무늬 투영 꼬리표·평면 틀 규칙은 엔진의 무늬 투영 기록과 요소·재질 읽기 코드에서,
  색 바꾼 무늬 규칙은 참조 뷰어의 무늬 색 바꾸기 코드에서. 꼬리표 위치·값 꼴은 사용자 컴퓨터의 SketchUp 26.2 파일로 직접 확인했다(아래 [무늬](#무늬텍스처-2026-10-16)).
목적은 상호 운용(뷰어에서 열기)을 위한 형식 분석뿐이다.

- 해석기: `src/` (`skpToScene(bytes, { name })` → `Scene3d`)
- 시험: `tests/` — 표본 파일은 넣지 않고, 아래 구조를 손으로 옮긴 작은 바이트로 시험한다(`tests/build.ts`, 쓰기 도구 본체는 앱의 예제 모형과 함께 쓰는 `src/app/skpwrite.ts`; 2020 이하는 `tests/mfcwrite.ts`).
- 표본 확인 스크립트·표본은 작업 중 `.runtime/skp/`에만 두었고 끝난 뒤 지웠다.

## 공통 머리(모든 판)

```
FF FE FF 0E  "SketchUp Model"(UTF-16LE, 14자)
FF FE FF nn  "{주.부.빌드}"(UTF-16LE), 예: {8.0.1}, {17.2.2555}, {21.0.339}
```

문자열 꼴: `FF` + `FFFE`(유니코드 표시) + 길이(1바이트, `FF`면 뒤에 u16, 그것도 `FFFF`면 u32) + UTF-16LE 글자. 2020 이하 판 본문의 모든 문자열도 같은 꼴이다.

## SketchUp 2021~2026: VFF + ZIP + TLV

### 머리 뒤 VFF 블록

```
"VFF" u16 길이(=8) | u16 1 | u16 하위 판 | u32 ?
```

하위 판(관찰): 21.0 → 8, 21.1 → 11, 22.0·23.0·23.1 → 13, 25.0·26.0·26.1 → 17. 끝 u32는 검사값처럼 보이지만 ZIP 부분의 CRC-32·Adler-32와 맞지 않았다(모름). 블록 바로 뒤에 ZIP이 시작한다.

### ZIP

- 표준 ZIP. 중앙 목록·지역 머리 위치는 **ZIP 시작 기준**(파일 기준 아님) → 끝 레코드 위치 − 중앙 목록 크기 − 중앙 목록 위치로 앞붙이 길이를 구한다.
- 압축은 DEFLATE(방식 8)만 보였다. 일반 목적 깃발 0 또는 6(데이터 서술자 없음). 이름은 비트 11 없이 UTF-8.
- 항목(관찰): `meta/model_thumbnail.png`, `meta/preview_thumbnail.png`, `meta/meta.dat`, `materials/<재질 이름>/material.xml`(+ 무늬 그림 jpg/png), `styles/<스타일>/style.xml`, `thumbnails/<컴포넌트>.png`, `scene_thumbnails/<장면>.png`, `classifications/*.skc`, `model.dat`.
- 해석기는 동기 함수라 DEFLATE를 직접 푼다(`inflate.ts`, RFC 1951만 보고 작성).
- 깃발에 데이터 서술자(비트 3)가 없어서 지역 머리에도 압축 크기가 있다 → 끝(중앙 목록·끝 레코드)이 잘렸거나 깨진 파일은
  ZIP 앞에서부터 지역 머리를 따라가며 항목을 찾을 수 있다(`scanZipLocal`). 이것은 공개 ZIP 구조만 쓴 것이다.
  마지막 항목이 잘렸으면 압축 흐름을 입력 끝 앞까지만 풀어 쓴다(`inflateRawPartial`, 입력 끝을 넘겨 읽기 시작한 곳 뒤 출력은 버림).

### material.xml

```xml
<mat:material name="[Color_A01]" type="0" colorRed="255" colorGreen="0" colorBlue="0"
  colorizeType="0" trans="1" useTrans="0" hasTexture="0" />
```

- 색은 `colorRed/Green/Blue`(0~255). 무늬 재질도 같은 속성이 있다(무늬 평균색으로 보이며 `avgColor`도 있다).
- 투명: `useTrans="1"`일 때 `trans`가 불투명도로 보인다(유리 0.04~0.52). 그런데 `trans="0" useTrans="1"`인 재질(firstaid의 Material__1~5)이 내장 미리보기에서 불투명하게 보여서, 해석기는 0<trans<1일 때만 알파로 쓴다(**확실하지 않음**).
- 태그 색은 `Layer_<태그 이름>` 재질로 들어 있다.
- `model.dat`의 재질 이름(32CC)은 꾸러미 폴더 이름과 같고, XML의 `name`은 원래 이름이다(예: `<Black>` → 폴더·model.dat는 `_Black_`, `*` → `_`, `<auto>` → `_auto_`). 해석기는 폴더 이름으로 먼저, XML 이름으로도 찾는다 — 표본 11개의 재질 240개가 모두 이어졌다. 화면 이름은 XML의 원래 이름을 쓴다.

### model.dat의 TLV 문법

```
[u16 꼬리표][u32 길이][길이 바이트 내용]   (리틀 엔디언)
```

- 뿌리는 꼬리표 `0x01F4`, 길이 = 파일 길이 − 6(모든 표본에서 일치).
- 내용은 자식 TLV의 나열이거나 값이다. 어느 꼬리표가 묶음인지는 적혀 있지 않다(해석기는 아는 경로로만 내려간다).
- 값 꼴: **번호**는 길이 1~8바이트의 가장 짧은 부호 없는 리틀 엔디언 정수(예: `2D1F` = 7981, `693707` = 472937) = SketchUp **영구 번호**(persistent id, 모형 전체에서 하나). 좌표·평면·변환은 f64 배열, 이름은 UTF-8, 깃발은 u8, 개수류는 i32.
  - 해석기는 8바이트를 넘거나 2^53 이상인 번호를 "찾지 못함"으로 둔다(JS 수로 정확히 나타낼 수 없다). 엔진은 8바이트를 넘으면 파일을 손상으로 친다.
- 몇몇 목록(`138E` 요소 차례, `714B`·`7150`·`7151` 장면, `3E84` 태그 폴더, `53FE` 치수 점 경로)은 [u8 크기 n][n바이트 번호]의 나열이다(n > 8이거나 범위를 넘으면 거기서 멈춘다).

### 확인한 규칙과 근거

- **고리 차례**: 모서리 쓰임을 차례로 따라가며 뒤집힘이면 (끝→시작), 아니면 (시작→끝)으로 잇는다. 표본 6개의 고리 130,813개가 모두 빈틈없이 이어졌다.
- **바깥 고리 = 첫 고리**: 고리가 둘 이상인 면에서 평면 법선 기준 넓이가 첫 고리만 양수·최대였다(면적 0인 퇴화 면 4개 제외).
- **변환 1966**(f64×13): 앞 9개는 3×3 **행 우선**(열이 축 벡터), 다음 3개는 이동, 끝 1개는 나눔수(표본 모두 1). 면에 붙인 컴포넌트에서 원점이 부모 면 위에 있을 때, 행 우선으로 읽은 z축만 면 법선과 맞은 경우 19건, 열 우선만 맞은 경우 0건.
- **깃발 07D3**: 보통 0x06. 비트 0x01 = 숨김(genb의 숨긴 인스턴스 22개가 모두 '3D Printer Build Volume' 안의 프린터 모형 — 한 번에 하나만 보이게 둔 것). 모서리의 **0x08 = soft(부드러움), 0x10 = smooth(매끈함 — 음영을 이어 칠함)**(엔진 ✔, 표준 파일 edge_flags: 0x0E soft, 0x16 smooth, 0x1E 둘 다). 해석기는 둘 중 하나라도 있으면 선을 그리지 않는다. **0x20 = 잠김**(인스턴스·주석, 엔진 ✔). 0x02·0x04는 그림자로 보인다(◐). 면의 0x40은 모름.
- **좌표 단위**: 내부 좌표는 언제나 인치(0.787402 = 20 mm 같은 값). 표시 단위 `UnitsOptions/LengthUnit`: 0 인치(meta.dat의 "Inches"와 일치), 2 mm(치수 글 '91.00 mm'와 일치), 3 cm, 4 m. 해석기는 2·3이면 mm, 4면 m로 바꾸고 나머지는 인치로 둔다.
- **기본 태그 = 태그 목록(3A99)의 첫째**(엔진 ✔, C API 비교). `3A9A`는 **활성(지금 그리는) 태그**다 — 모든 표본에서 첫째(Layer0, 한 표본은 'Layer00')와 같았던 것은 Layer0을 활성으로 두고 저장했기 때문이다. 2026-10 전에는 3A9A를 기본 태그로 썼다. 요소에 07D2가 없거나 기본 태그 번호면 감싼 인스턴스의 태그를 따른다.
- **재질 물려받기**: 면 앞 재질이 없으면 감싼 인스턴스 재질을 쓴다(telephone 표본의 버튼 색이 이렇게 해야 미리보기와 같다).
- **눈 확인**: firstaid·telephone·tulostin·classroom·gizo를 소프트웨어로 그려 내장 미리보기와 견주었다 — 형상·배치·색이 맞았다.

참조 꼬리표는 클래스와 관계없이 2(또는 6)바이트라 해석기는 모서리 정점·곡선, 고리의 모서리 참조가 맞지 않으면 그 참조만 버리고 이어 읽는다.

**곡선의 모서리 차례**(엔진 ✔): 곡선에 드는 모서리는 같은 묶음에서 0BBB가 그 곡선 번호인 모서리들이다. 첫 모서리(4A3B)에서 출발해 이어지는 모서리를 따라가며, 끝 모서리(4A3C)가 첫 모서리의 끝 정점만 공유하면 시작 정점 쪽으로 떠난다(닫힌 곡선을 바른 방향으로). 호 자료가 있고 닫혔으면(모서리 ≥ 3, 첫·끝 모서리가 정점 공유) 원, 아니면 호, 4A3A = 1이면 다각형.

**치수 풀이**(엔진 ✔, 규칙 일부 ◐): 선형 치수의 잰 축 u = (5BD1 = 1) x축 · (2) 법선×x축 · (0·없음) 끝점 − 시작점, 띄움 = unit(법선 × u) × 5BD2(인치). 반지름·지름은 5DC1 모서리의 곡선(호)에서 중심 c·x축·법선을 얻어 dir = cosθ·x̂ + sinθ·(n × x̂), 호 위 점 = c + r·dir, 글 쪽 점 = c + r·L·dir. 붙은 점(5209 = 2·4)은 대상 정점(또는 모서리 가운데)을 경로의 인스턴스 변환으로 안쪽부터 옮긴다. 못 찾으면 저장 위치(520A).

### 무늬(텍스처, 2026-10-16)

출처: 엔진의 무늬 투영 기록과 꼬리표·요소·재질 읽기 코드, 참조 뷰어의 무늬 색 바꾸기 코드
(같은 저자의 프로젝트, 허락받아 참고). 꼬리표 위치·값 꼴은 이 컴퓨터의 SketchUp 26.2 파일 셋(사용자 자료, 읽기만 함 — 저장소·시험에 넣지 않음)에서
직접 확인했다: 면 수백 개가 아래 경로에 무늬 위치를 갖고 있었고 종류 0·1·3이 보였다.

**material.xml 무늬**(관찰과 일치):

```xml
<mat:material name="이녹스" type="1" colorRed="184" … colorizeType="0" … hasTexture="1">
  <mat:texture textureFilename="C:\…\inox.png" xScale="23.622047244094489" yScale="13.267716535433072" avgColor="4290295992">
    <mat:images><mat:image id="1" path="./inox.png" file_name="inox.png"/></mat:images>
  </mat:texture>
  <mat:pbrMR …>…</mat:pbrMR>
```

- `xScale`·`yScale` = 무늬 한 장의 가로·세로(**인치**, 23.622… = 600 mm). `avgColor` = 원래 그림 평균색(ABGR 정수, 부호 있게 적힌 것도 있다).
- `type` 0 색 · 1 무늬 · 2 색을 바꾼 무늬. type 2는 `colorRed…`가 바꾼 색이고 `colorizeType` 0 = shift(기본), 1 = tint.
- 그림은 재질 폴더 안 `<image path="./…">`. 2025 이후 PBR 재질은 같은 폴더에 다른 그림(법선 등)도 둘 수 있어 이름으로 고른다.

**면 무늬 위치**(꼬리표 경로, 값 꼴은 직접 확인):

```
면 0DAC → 바탕 07D0 → 05DC → 05DD(속성) → 36B1 → 36B2 → 2710 무늬 위치
  2710 ─ 36B0(빈 것), 2711 앞 · 2712 뒤 ─ 2713 ─ 2714 종류 i32, 2715 행렬 f64×9, 2716 방향 f64×3, 2717 핀 목록(2718: 2719 점 f64×2, 271A uv f64×2)
```

- 행렬 2715는 무늬 좌표(인치) → 면 평면 틀 좌표의 3×3 동차 변환이고 **열 우선**으로 적혀 있다. 종류: 0 그대로, 1 위치 잡음, 2·3 방향(2716)으로 투영.
  무늬를 지운 재질의 면에도 남아 있으므로, 해석기는 그쪽(앞·뒤) 재질이 무늬 재질일 때만 읽는다.
- 면 평면 틀(엔진 기록, SketchUp C API로 잰 규칙): x = (Z × n) 정규화 — n의 x·y가 모두 1e-3보다 작으면(거의 수평) (Y × n), y = n × x.
  원점은 정의(컴포넌트) 원점, 좌표는 정의 좌표(인치)라 인스턴스를 늘리면 무늬도 늘어난다.
- 무늬 좌표: (U, V, Q) = diag(1/가로, 1/세로, 1) · M⁻¹ · (p·x, p·y, 1), u = U/Q, v = V/Q(v는 그림 위쪽으로). 종류 2·3은 n 대신 2716 방향으로 틀을 잡는다.
  저장된 투영이 없으면 M = 단위 행렬(**기본 투영**). M을 뒤집을 수 없으면 기본 투영으로 칠하고 경고한다.
- M의 마지막 줄이 (0, 0, 1)이 아니면(사진 맞춤처럼 일그러뜨린 무늬) Q가 면 위에서 바뀐다 → 정점마다 (u·q, v·q, q)를 두고 조각마다 나눈다(원근 보간).
  Q의 부호가 면 위에서 바뀌거나 0에 가까우면(최솟값이 최댓값의 1e-3 아래) 원근 없이 칠하고 경고한다.
- 재질 물려받기와 무늬: 앞·뒤를 따로 칠한다(2026-10-22). 그쪽 자기 재질이면 그쪽 저장된 투영(없으면 기본 투영)과 그 재질의 무늬 크기,
  인스턴스 재질을 물려받으면 기본 투영과 물려받은 재질의 무늬 크기로 칠한다(참조 뷰어의 규칙과 같다). 재질이 없는 쪽은 스타일 앞면·뒷면 색.
  뒷면은 코어 `backColor`·`backTexture`·`backUvs`로 그린다(삼각형을 면 법선 쪽에서 반시계로 감아 두어 시계 방향으로 보이는 쪽이 뒷면).
  예전(2026-10-21까지)에는 한 면을 한 재질(앞 → 물려받기 → 뒤)로 양면을 같게 칠했다.

**색 바꾼 무늬**(참조 뷰어의 기록 — SketchUp 재질 미리보기와 견주어 맞춘 규칙): HLS로 C = 재질 색, A = 그림 평균색일 때
shift는 h' = h + (h_C − h_A), tint는 h' = h_C, l' = clamp(l + l_C − l_A), s' = s_C < s_A ? clamp(s · s_C / s_A) : clamp(s + s_C − s_A). 알파는 그대로.
화면은 해석 워커에서 그림을 풀어(OffscreenCanvas) 화소 색을 바꾸고, 못 풀면 무늬를 빼고 재질 색(= 바꾼 평균색)으로 칠한다.

## SketchUp 3~2020: MFC CArchive 꼴

해석기: `src/mfcstream.ts`·`mfcstate.ts`·`mfcmodel.ts`·`mfcview.ts`·`mfcannot.ts`(`readMfcModel`). 2021+ 해석기와 같은 중간 모형(`SkpModel`)을 내므로 장면 출력(`scene.ts`·`scene-meta.ts`)과 화면은 그대로 쓴다.
아래 "확인한 것"은 처음(2026-09) 공개 표본 바이트로 본 것이고, "엔진에서 옮긴 것"이 해석기가 따르는 규칙이다.

### 확인한 것

- 압축 없음(본문 안의 zlib 흐름은 PNG 그림뿐). 숫자는 f64 리틀 엔디언(정육면체 표본에서 12.0 = `00..28 40`).
- 머리 문자열 뒤: 16바이트(파일마다 달라 GUID로 보임), 빈 문자열(`FF FE FF 00`), u32(유닉스 시각으로 읽으면 표본 저장 시점 근처).
- 이어서 객체 직렬화. 객체 꼬리표는 MFC CArchive의 공개된 꼴과 일치했다(정육면체 v8에서 번호 계산이 맞음):
  - `FFFF` + u16 스키마 + u16 길이 + ASCII 클래스 이름 = 새 클래스(이어서 그 클래스의 객체 내용)
  - `8000 | k` = 이미 나온 클래스 k의 새 객체
  - 그 밖의 u16 = 이미 나온 객체 번호 참조(0 = 없음)
  - 클래스와 객체가 번호 하나를 같이 센다(정육면체 v8: CEdge 클래스 0x11, 모서리 0x12, CVertex 클래스 0x13, 정점 0x14·0x15, 다음 모서리 0x16 …).
- 첫 객체 `CVersionMap`: (클래스 이름 문자열, i32 스키마) 쌍의 나열이 `End-Of-Version-Map`까지. 판마다 각 클래스의 스키마 번호를 알려 준다(아래 표).
- 이어지는 큰 차례(모든 표본 같음): `CDib`(미리보기 PNG: i32 4, i32 길이, PNG) → 모형 설정(이름 있는 값 묶음: 'PageOptions', 'UnitsOptions' …, 값 앞에 형 바이트 04 i32·06 f64·07 bool) → `CAttributeContainer`/`CAttributeNamed`(속성 사전) → `CCamera` → (렌더링·그림자 설정은 클래스 꼬리표 없이 바로 이어 씀) → `CMaterial`들 → `CLayer`들 → `CComponentDefinition`들(각자 요소 목록) → 모형 요소 목록(개수 i32 + 객체들) → `CSkFont` → `CSkpStyle` …
- 형상 객체(정육면체 v8, CEntity 3·CDrawingElement 9):
  - `CVertex`: [u16 0][f64 x][f64 y][f64 z]
  - `CEdge`: [바탕 12바이트][시작 정점 객체 또는 참조][끝 정점][u16]
  - `CFace`: [바탕 12바이트][f64×4 평면][i32 고리 수?][`CLoop` 객체 …]
  - `CLoop`: [u16 0][u8 1][u8 1] 뒤에 `CEdgeUse`가 줄줄이: [u16 0][모서리 참조][u8 뒤집힘][고리 참조]
  - 2017(CEntity 5)부터 요소 바탕에 [u8 1][u32 영구 번호]가 붙는다(정점 0x0B, 0x0C …).
- 형상 클래스의 스키마는 3~20 내내 같았다(CVertex 0, CEdge 2, CEdgeUse 1, CFace 3, CLoop 1). 바뀐 것은 바탕(CEntity 2→3→5, CDrawingElement 8→9), 인스턴스(CComponentInstance 3→6), 모형·설정(CSketchUpModel 10→29, CRenderingOptions 22→39, CViewPage 6→13) 쪽이다.

### 엔진에서 옮긴 것(2026-10, 2020 이하)

엔진 legacy 해석기는 판마다 기능 하나씩 담은 표준 파일을 SketchUp 2026 C API로 7·8·2013~2020 형식에 저장해 C API 기대값과 견주어 맞췄다(엔진 ✔).
해석기는 그 규칙을 옮겼고, 엔진 표준 파일 34개(기본 묶음의 8·17·20 판과 옛 판 묶음의 7·13~20 판, 읽기 전용)를 이 해석기로 읽어
면·모서리·고리·정점·깃발·재질·태그(색·숨김·폴더·선 종류)·정의(종류·GUID·동작)·인스턴스(변환·이름·GUID·깃발)·곡선·문자·치수 점·보조선·단면·장면(깃발·카메라·숨긴 태그·숨긴 개체·활성 단면·스타일)·
모형 카메라·스타일·단위가 기대값과 같은 것을 확인했다(2017 전 파일의 영구 번호는 C API가 열 때 새로 매기므로 견주지 않았다). 표준 파일은 저장소·시험에 넣지 않았다.

**객체 흐름** ✔:
- 머리 문자열 둘 뒤에 16바이트 모형 GUID, CString 마지막 저장 경로, u32 저장 시각. 그 뒤가 **MFC `CArchive` 객체 흐름 하나**이고 기록 길이가 없다.
- 객체 꼬리표(u16): `0000` 없음 · `FFFF` 새 클래스(u16 스키마, u16 이름 길이, ASCII 이름) 뒤에 그 객체 · `8000 | n` 칸 n 클래스의 새 객체 · `n` 이미 읽은 칸 n 참조 · `7FFF` + u32(0x7FFF 이상의 칸, `80000000`이 서면 클래스).
  클래스와 객체가 칸 번호 하나를 같이 세고(칸 1부터), **객체는 칸을 먼저 받고 칸을 읽는다** — 모서리가 곡선을, 모서리 사용이 자기 고리를 되가리킬 수 있다.
- CString: u8 길이, `FF` + u16, `FF FFFF` + u32. `FF FFFE`가 앞에 오면 UTF-16LE(그 뒤 길이를 같은 꼴로). 좁은 글은 latin-1로 읽는다.
- 스키마는 첫 객체 `CVersionMap`(클래스 이름 → i32, `End-Of-Version-Map`까지)이 알린다. 클래스 꼬리표의 스키마 칸은 쓰지 않는다(내려 저장한 파일은 지금 판 스키마를 적는다).
- 모든 요소는 **CEntity 앞머리**로 시작한다: `CAttributeContainer` 포인터, (CEntity 5 이상 = 2017+) 영구 번호 = 바이트 가면 u8 + 가면이 고른 바이트(리틀 엔디언).
  그리는 요소는 이어서 **CDrawingElement**: `CMaterial` 포인터, 깃발 6바이트(0 숨김, 3 soft, 4 smooth, 5 잠김), `CLayer` 포인터.
- 읽는 함수가 없는 클래스는 건너뛸 수 없다 — 해석기는 거기서 멈추고 그 앞까지 읽은 형상을 그린다(경고, 손상은 아님). 잘림·맞지 않는 참조는 손상(`meta.damaged`)으로 본다.

### SketchUp 3~6 조사(2026-10-21)

참조 뷰어 쪽에 있던 옛 판 표준 파일(3~6 판, 판마다 같은 기능 파일 28개 + SketchUp C API 기대값, 읽기 전용)을 7·8 판 같은 파일과 바이트로 견줬다.
판별 클래스 스키마(`CVersionMap`)는 이렇다(7과 다른 것만):

| 판 | 모형/렌더링 | 7과 다른 클래스 스키마 |
| --- | --- | --- |
| 6 | 18/32 | `CAttributeNamed` 0(7은 1), `CBackgroundImage` 1(9), `CComponentBehavior` 4(5) |
| 5 | 12/28 | 6의 것 + `CCamera` 4, `CDib` 2, `CDimension` 0, `CDimensionLinear` 4, `CSkFont` 0, `CTextStyle` 4, `CTexture` 4, `CViewPage` 9, `CSkpStyle`·`CSkpStyleManager`·`CWatermarkManager`·`CBackgroundImage` 없음 |
| 4 | 12/25 | 5의 것 + `CComponentInstance` 3, `CDrawingElement` 8 |
| 3 | 10/22 | 4의 것 + `CAttribute*`·`CCamera`·`CFaceTextureCoords`·`CPageList` 없음, `CEntity` 2, `CLayer` 1, `CCurve` 3, `CComponentBehavior` 3, `CThumbnail` 0 |

**SketchUp 6 → 읽는다** ✔(표준 파일 28개 모두 면·모서리·고리·정점·곡선·인스턴스 변환·이름·정의·태그·재질·단위·카메라·장면 수가 C API 기대값과 같고, 장면 출력은 7 판 같은 파일과 바이트까지 같았다. 무늬 위치 10쪽도 C API 투영과 같다):
- 모형 본문: 12바이트, 미리보기 `CDib`, **10바이트**(7은 14), 설명, 그 뒤 바로 `CCamera` — 설정 묶음·`CAttributeContainer`(ModelProperties)·두 번째 `CDib`가 없다(모형 이름도 없다).
- 렌더링 덩어리(`CRenderingOptions` 32): **189바이트** — 35(197바이트)의 앞 181바이트와 같고 그 뒤 f64 하나(8바이트)가 없다. 칸 자리는 33~36과 같다.
- `CComponentDefinition` 동작(`CComponentBehavior` 4): **38바이트** — 늘이지 않음 마스크(34의 u32)가 없다.
- `CAttributeNamed` 0: 끝 u32가 없다.
- 모형 꼬리: 축 뒤 69바이트 가운데 63바이트 다음에 **설정 묶음**(단위·장면 넘기기 — 7이 머리에 쓰는 것과 같은 꼴)이 끼고, 그 뒤 6바이트. 나머지(그림자·장면·글꼴·스타일)는 7과 같다.
- 모서리 깃발은 7과 같은 저장 바이트다(기대값 파일은 숨김·soft·smooth를 다른 수로 적지만 7·6 모두 같은 차이라 해석 차이가 아니다).

**SketchUp 3~5 → 아직 읽지 않는다**(시간을 정해 본 결과):
- 5: 머리가 6보다 4바이트 짧고(12 → 8바이트), `CCamera` 4는 설명 글 뒤 그림 너비·2점 투시·24바이트가 없다. 렌더링 덩어리 28은 배경색이 12(6은 13)부터이고 안개 칸 등이 빠져 칸 자리가 판마다 다르다.
  그 밖에 `CDib` 2·`CTexture` 4(무늬)·`CViewPage` 9(장면)·`CDimensionLinear` 4·`CSkFont` 0·`CTextStyle` 4와 스타일 클래스가 없는 꼬리를 하나씩 맞춰야 한다.
- 4는 5에 `CComponentInstance` 3·`CDrawingElement` 8(그리는 요소 깃발)이, 3은 속성·무늬 위치·장면 목록 클래스가 없고 `CEntity` 2·`CLayer` 1까지 다르다.
- 판마다 표준 파일 28개 + C API 기대값이 있어 같은 방법으로 맞출 수는 있다(판마다 1~2일 추정). 그때까지 앱은 판과 다시 저장 안내를 띄운다.

**중간 모형 채우기** ✔:
- 요소 묶음: 모형 뿌리와 정의마다 하나. 정점·모서리 값은 (묶음, 차례)를 묶은 수라 다른 묶음을 가리키면 손상이다. 면은 저장된 평면·고리 차례를 두고 바깥 고리를 앞으로 옮긴다. 고리 정점은 2021+처럼 뒤집힌 모서리 사용이면 끝 정점에서 시작한다.
  모서리 깃발은 2021+ 꼴로(0x01 숨김, 0x08 soft, 0x10 smooth), 인스턴스·주석은 0x01 숨김·0x20 잠김. 영구 번호는 2017+만 저장값.
- 태그: 모형 목록에서 기본 태그(`Layer0`/`Untagged`)를 맨 앞으로. 정의의 태그 목록은 쓰지 않는 사본이라 같은 이름의 모형 태그로 잇는다. 색은 줄 안 색 재질의 알파 바이트가 있으면 그 색, 아니면 회색(64, 64, 64). 선 종류는 이름(`Solid Basic`은 없음). 2020 폴더는 뿌리를 빼고 앞 순회.
- 재질: 알파 쓰기일 때만 불투명도 = 1 − 투명도(2021+ material.xml 읽기처럼 0.15 아래는 0.15). 색 알파 바이트가 0인 무늬 재질은 무늬 평균색. 무늬 그림은 `readSkpImages`로(날 DIB는 BMP 파일 머리를 붙인다).
- 정의 종류: `CImage`가 놓은 정의는 그림(동작 없음), `CGroup`만 쓰면 그룹, 그 밖은 컴포넌트. GUID는 2021+처럼 22자 IFC 글.
- 곡선: 모서리를 곡선 포인터로 모아 잇는다 — 열린 곡선은 자유 끝에서(호는 시작각 점에 가까운 끝), 닫힌 호는 시작각 정점에서 법선 둘레 반시계로. 반지름 = |x축|.
- 스타일: 덩어리의 RenderMode·무늬·X-ray·숨긴 형상·단면 채우기와, 스타일 값이 없을 때의 색·켜기(배경·모서리·앞뒷면·하늘·지면·윤곽선)를 2021+ 렌더링 레코드 꼬리표 값으로,
  `CSkpStyle` 설정을 style.xml 항목 글로 옮겨 `styles.ts`가 2021+와 똑같이 푼다. 모형은 작업 사본(없으면 스타일 목록 끝), 장면은 장면의 스타일 사본. 이름은 활성 스타일 이름.
- 장면: 깃발은 2021+ 꼴로(16 → 128 + 256). 숨긴 태그 = 저장된 태그 목록(최종 태그 차례). 숨긴 개체·활성 단면은 영구 번호로 — **2016 이하 파일은 영구 번호가 없어 대상에 음수 임시 번호를 붙여 잇는다**(엔진은 이런 장면의 숨긴 목록을 버린다).
  전환·지연이 음수면 Model Info > Animation(`PageOptions`·`SlideshowOptions`). 2020 장면 미리보기는 `scene_thumbnails/<칸>-<이름>` 경로로 그림과 잇는다.
- 단위: `UnitsOptions`(2021+와 같은 코드). 2019 전 파일은 넓이·부피 단위가 없어 SketchUp처럼 길이 단위와 소수 둘째 자리로 채운다.
- 이름·설명: 모형 기록 사전의 `ModelProperties.Name`, 본문 설명. 2018 전 파일은 단면 이름이 없어 SketchUp처럼 `Section N`·`N`을 붙인다.
- 주석: 모서리에 붙은 점은 모서리 매개변수로, 정점에 붙은 점은 그 정점으로 푼다. 다른 대상에 붙은 점은 저장값(경고). 지시선 없는 글은 화면 글. 지름·반지름 = (중심, 지시선 각의 호 위 점, 글 거리 × 반지름의 점). 선형 치수 배치는 2021+와 같은 `linearLayout`.

**남은 틈**: SketchUp 3~5(모형 스키마 18 미만)는 읽지 않는다. `CRelationship`·`CDib` 꼴 0·1·4 밖은 거기서 멈춘다(엔진 말뭉치에도 없었다).
읽기만 하고 쓰지 않는 것: 그림자·위치(`CShadowInfo`), 축, 글의 지시선 끝, 덩어리의 글·치수 보이기와 흐림 값, 모형 꼬리의 스타일 뒤.

## 실현 가능성

- **2021~2026: 됨(이번에 구현).** 길이가 붙은 TLV라 모르는 꼬리표는 건너뛰고, 형상 꼬리표는 21.0~26.1 모든 표본에서 같았다. 태그 숨김·장면·문자·치수·스타일은 2026-10에 엔진 지식으로 붙였다. 무늬는 2026-10-16에 붙였다(무늬 절). 남은 일(그림자·위치, 워터마크)은 같은 방식으로 하나씩 붙일 수 있다(각 0.5~2일).
- **7·8·2013~2020: 됨(2026-10, 엔진 지식).** 길이 표시가 없는 객체 그래프라 나오는 모든 클래스를 읽어야 하는데, 엔진이 판마다 C API와 견주어 맞춘 배치를 옮겨 엔진 표준 파일 34개에서 같은 값을 얻었다.
  낯선 클래스를 만나면 거기서 멈추고 그때까지의 형상을 돌려준다. 남은 위험: 표준 파일은 기능 하나씩 담은 작은 모형이라, 실제 큰 옛 모형(엔진 말뭉치 78개 중 1개는 깨진 파일이었다)에서 새 클래스를 만날 수 있다.
- **6: 됨(2026-10-21).** 7과 다른 곳이 넷뿐이라(아래 조사) 표준 파일 28개가 C API 기대값과 같았다.
- **3~5: 읽지 않는다.** 머리·카메라·렌더링 덩어리·그림·무늬·장면·치수·글꼴 배치가 판마다 달라(아래 조사) 판별 배치를 새로 알아야 한다. 엔진도 읽지 않는다.
